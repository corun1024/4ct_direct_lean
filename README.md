# The Four Colour Theorem, the Coq way, in Lean 4

A port of Georges Gonthier and Benjamin Werner's Coq proof of the Four Colour Theorem to Lean 4
that keeps the Coq proof's method for the computational half, with Mathlib for the mathematical
foundations. The kernel that checks it is [lazylean](https://github.com/corun1024/lazylean), a
Lean 4 kernel with a lazy, Coq-style reduction engine; Lean's own kernel is switched off. That
is the point of the repository, and this file explains why.

```
137 765 declarations exported from Lean, 137 765 accepted by lazylean, 0 rejected
    633 reducibility checks evaluated in the kernel: 77 core-hours, 34 GB at the peak
    fourColorTheorem depends on Classical.choice, Quot.sound, propext, and nothing else
```

The statement is Gonthier's, clause for clause, over Mathlib's reals: a map is a partial
equivalence relation on points of ℝ², a simple map has open connected classes, and a
four-colouring is a coarser map that separates regions sharing a non-corner border point. It
lives in `FourColor/RealPlane.lean`, 195 lines that import three Mathlib topology modules and
nothing from this repository, so auditing what was proved means reading that one file.

## Two ways to check 633 configurations

Every proof of the Four Colour Theorem since Appel and Haken has two computational halves.
Discharging shows that every planar cubic map contains one of a finite list of configurations,
and reducibility shows that each of those 633 configurations cannot appear in a minimal
counter-example. Gonthier's Coq proof establishes reducibility by *running a program inside the
kernel*: `check_reducible` computes the Kempe-chain closure of a configuration's ring colourings
over trees of traces and chromograms, and the kernel's conversion check evaluates
`check_reducible cf = true` for each configuration. Coq's kernel was given a bytecode virtual
machine for that proof, and its lazy reduction machine can do it too, more slowly.

[corun1024/4ct](https://github.com/corun1024/4ct) ports the whole proof to Lean 4 and Mathlib,
but not that part. Lean's kernel normalises terms by substitution and keeps every intermediate
term for the life of a declaration; on `check_reducible` it needs 166 GB at ring size 12 and
does not finish rings 13 and 14 at all. So that repository replaced the Kempe-closure program
with a certificate scheme designed around what Lean's kernel is good at, GMP-accelerated
arithmetic on `Nat` literals millions of bits wide: a ring's trace set becomes one natural
number, Kempe flips become shifts and masks, and 633 generated certificate modules reach
`CfReducible` through two soundness theorems proved once. It works, and it is a different
proof of reducibility from Gonthier's.

This repository takes the other road. `checkReducible` is Gonthier's `check_reducible`, ported
function for function, and reducibility is settled the way `cfreducible.v` and the `job*.v`
files settle it: by evaluating it on each configuration in the kernel. The kernel is lazylean,
which runs a Krivine machine with call-by-need thunks after Coq's `cClosure`, and it gets
through the largest configurations in a few minutes and about 21 GB.

## What this repository is

The mathematics is the mathematics of corun1024/4ct, unchanged: hypermaps and their Euler
formula, planarity and the Jordan curve property, Kempe chain surgery, the reduction from the
plane to finite maps by compactness, the configuration database and the seven discharging
presentations, all over Mathlib's structures rather than transliterated MathComp. What was
removed is the certificate machinery (`FourColor/Bulk/`, `FourColor/Mask*.lean`,
`FourColor/Cert*.lean`, the C generators and their scripts). What was added is small:

- `FourColor/Reducible/`: 49 job modules, 10 task modules and `All.lean`, mirroring
  `job001to106.v` … `job623to633.v`, `task001to214.v` … `task589to633.v` and `reducibility.v`
  of the Coq proof, generated by `scripts/gen_reducible.py`.
- One line in `lakefile.toml` that switches Lean's kernel off, and `scripts/verify.sh`, which
  is where the proof is checked.

`FourColor/CfReducible.lean` lost its depth-limited and iterated variants of the check
(`checkReducibleAt`, `checkReducibleNum`), which were shortcuts for Lean's kernel with no
counterpart in the reference; `checkReducible` and its soundness theorem
`check_reducible_valid` are Gonthier's `check_reducible` and `check_reducible_valid`.

## How the reducibility check is wired in

A job module is the Coq job file, one theorem per configuration and then the range lemma the
`CheckReducible` tactic proves:

```lean
theorem red_cf623 : checkReducible cf623 = true := by decide +kernel
…
theorem red_cf633 : checkReducible cf633 = true := by decide +kernel

/-- Configurations 623 to 633 are reducible. -/
theorem red622to633 : ReducibleInRange 622 633 theConfigs :=
  check_reducible_in_range fun i =>
    match i with
    | 0 => Or.inr red_cf623
    …
    | 10 => Or.inr red_cf633
    | n + 11 => Or.inl (Nat.le_add_left 11 n)
```

`check_reducible_in_range` is the reference's lemma of that name: a disjunction over the
indices of a slice of the configuration list, discharged index by index, turns into
`reducible_in_range`. The task modules chain the jobs with `cat_reducible_range` the way the
`CatReducible` tactic does, `All.lean` chains the tasks the way `reducibility.v` does, and
`Complete.lean` feeds `reducible_all : ReducibleInRange 0 633 theConfigs` to the theorem.

One theorem per configuration rather than one per job is the only deliberate departure in
this part, and it is about memory: a kernel holds the working set of one declaration at a
time, and the ring-14 configurations each need about 21 GB. In Coq the same is achieved by the
job files themselves being small.

## Lean elaborates, lazylean checks

`lakefile.toml` sets `debug.skipKernelTC = true` for every module. Lean still elaborates
everything, so tactics run, terms are built, and `lake build` produces oleans, but the kernel
is never asked whether a term has the type it claims. In particular `decide +kernel` no longer
evaluates anything: it produces the proof term `of_decide_eq_true (Eq.refl true)` and hands it
to `addDecl`, which stores it unchecked. The whole development elaborates in about four
minutes on 64 threads.

The checking happens afterwards, in `scripts/verify.sh`:

1. `lean4export` writes the dependency closure of `FourColor.fourColorTheorem` and of the
   audit theorems (287 MB), and separately the closure of the 633 reducibility theorems alone
   (9 MB).
2. lazylean checks the first export in shards, with every declaration named `FourColor.red_cf*`
   listed as trusted, so that the expensive ones are not checked twice.
3. lazylean checks each of those declarations on its own from the second export, one process
   per declaration, scheduled by ring size under a memory budget
   (`scripts/schedule_reducible.py`).
4. `scripts/summarize.py` refuses to write a clean summary unless every declaration in both
   steps was accepted, lists the axioms the export declares, and prints the theorem's type as
   lazylean read it.

Every declaration in the closure is checked exactly once, by lazylean, from the export Lean
produced. Nothing is checked by Lean's kernel, and nothing is checked by neither. The trusted
base is therefore lazylean plus lean4export, and lazylean's own testing, against the Lean
Kernel Arena's soundness suite, Init, Std, Lean, Mathlib and a differential fuzzer, is
described in its README.

`scripts/check.sh` keeps the old guards: no `sorry`, no `native_decide`, no `axiom`, no
`partial`, `unsafe` or `opaque`, `debug.skipKernelTC` nowhere but the lakefile, `Check.lean`'s
axiom walk over the elaborated environment, and the theorem present with the right statement.
It then demands the verification summary.

## The verification run

The whole development was exported with `lean4export` and checked by lazylean, twice over:
once as a 16-shard sweep of the dependency closure of `fourColorTheorem`, and once as 633
separate processes for the reducibility theorems, whose memory demands are too different from
each other to share a schedule. The run below is on a rented 64-thread AMD EPYC 7B13 with
251 GB of memory, 22 September 2026. `verification/SUMMARY.md` is the summary the run wrote,
and `verification/ring_sizes.tsv` the per-configuration ring sizes that schedule it.

| | declarations | failed | CPU | wall | peak memory |
|---|---|---|---|---|---|
| the closure, 16 shards | 136 499 | 0 | 0.51 h | 128 s | 1015 MB per shard |
| the 633 reducibility checks | 1 266 | 0 | 76.94 h | 3.4 h | 34 318 MB |

The reducibility cost is all in the three largest ring sizes, and it grows by roughly a factor
of four per ring size:

| ring size | configurations | total CPU | slowest | peak memory |
|---|---|---|---|---|
| 6 | 1 | 1 s | 1 s | 35 MB |
| 7 | 1 | 1 s | 1 s | 38 MB |
| 8 | 5 | 7 s | 2 s | 44 MB |
| 9 | 8 | 30 s | 4 s | 68 MB |
| 10 | 31 | 419 s | 18 s | 149 MB |
| 11 | 81 | 4 543 s | 92 s | 602 MB |
| 12 | 175 | 40 286 s | 351 s | 2 170 MB |
| 13 | 194 | 77 835 s | 851 s | 7 426 MB |
| 14 | 137 | 153 534 s | 1 505 s | 34 318 MB |

The most expensive single configuration is `cf613`, ring size 14, at 1 505 s and 31.6 GB; the
worst for memory is `cf281` at 34.3 GB. Those two numbers are what a scheduler has to respect:
running the ring-14 checks more than five or six at a time on this machine would have swapped.

Scheduling aside, the run is unremarkable, which is the claim being made. No declaration was
rejected, none was declined, and the axiom listing of the exported theorem is the standard
three. Lean's kernel never looked at any of it.

## The three kernels on the same computation

This table is the reason the repository exists. `checkReducible cfNNN = true`, checked as a
bare `Eq.refl true` by three kernels on the same 32-core machine (a Threadripper 3970X), one
configuration per process. The Coq columns are Gonthier's `check_reducible` under Coq's lazy
kernel and under its bytecode VM. lazylean is run with memoisation off and original closures
dropped (`LL_MEMO=0 LL_ORIG=none`), which is how `scripts/verify.sh` runs it.

| configuration | ring size | Coq lazy kernel | Coq VM | Lean kernel | lazylean, first build | lazylean, current |
|---|---|---|---|---|---|---|
| cf001 | 6 | 1.1 s | 1.0 s | 4.0 s / 2 GB | 0.9 s / 35 MB | |
| cf003 | 8 | 1.3 s | 1.0 s | 10 s / 2.9 GB | 3.0 s / 79 MB | |
| cf006 | 9 | 1.7 s | 1.0 s | 26 s / 4.9 GB | 9.9 s / 161 MB | 0.9 s / 58 MB |
| cf009 | 10 | 3.1 s | 1.1 s | 92 s / 13 GB | 25 s / 524 MB | 3.5 s / 137 MB |
| cf015 | 11 | 5.2 s | 1.2 s | 328 s / 43 GB | 139 s / 3.6 GB | 13.0 s / 395 MB |
| cf020 | 12 | 13 s | 1.6 s | 31 min / 166 GB | 125 s / 2.4 GB | 53 s / 1.2 GB |
| cf023 | 13 | 51 s | 3.5 s | killed at 178 GB | 513 s / 9.5 GB | 217 s / 4.4 GB |
| cf110 | 14 | 260 s | 16 s | killed at 178 GB | 44 min / 41 GB | 18 min / 21 GB |

The 633 configurations are not evenly spread over that ladder: 137 of them have ring size
14, 194 have 13 and 175 have 12, so the last three rows are nearly all of the cost. Lean's
kernel cannot check this proof. Coq's lazy kernel would take about four core-hours, its VM a
fraction of one, and lazylean took 77 on the slower-per-core machine the run below used. The gap between lazylean and Coq's lazy kernel is
the machine's per-step constant, thunk and environment allocation and reference counting
against an OCaml minor heap; lazylean's README has the profile.

`scripts/synth_decide.py` is how the ladder was run before the job modules existed: it writes
`checkReducible cfNNN = true := Eq.refl true` straight into an export, with no elaborator
involved.

## Reproducing

```
./build.sh
```

does everything: Mathlib from the cache, `lake build` with the kernel off, the export, the
lazylean run, and the checks. It needs [elan](https://github.com/leanprover/elan), `python3`,
a built [lazylean](https://github.com/corun1024/lazylean) (`LAZYLEAN=/path/to/lazylean`,
default `~/lazylean/build/lazylean`) and a built
[lean4export](https://github.com/leanprover/lean4export) at the toolchain in `lean-toolchain`
(`LEAN4EXPORT=…`, default `~/lean4export/.lake/build/bin/lean4export`), patched with
`scripts/hexparse_patch.py` from the lazylean repository so that it writes long `Nat` literals in
hexadecimal. Budget about 80 core-hours and 190 GB of memory for the reducibility step;
`JOBS` and `MEMORY_GB` scale it, `SHARDS` the closure step. The summary lands in
`verification/run/SUMMARY.md`; the committed one from the run described above is
`verification/SUMMARY.md`.

To regenerate the job modules after changing the partition or the template:
`python3 scripts/gen_reducible.py`.

## What differs from the Coq proof

Everything corun1024/4ct's README lists under "Idiomatic Mathlib, not transliterated MathComp"
still applies: the four colours are an `AddCommGroup`, a hypermap is three `Equiv.Perm`s,
orbit counts are `Nat.card` of a quotient, boolean reflection is `Decidable`, and two unused
converses (`Jordan_planar`, `Jordan_WalkupE`) are not ported. The statement is over Mathlib's
ℝ rather than an abstract real model, and the finite-to-general step uses an ultrafilter in
place of the reference's choice-free lexicographic minimum.

Reducibility now follows the reference: the same check, the same job partition, the same
chaining lemmas. Two things remain different. Each configuration is its own theorem, for
memory, where a Coq job file evaluates several in one lemma. And the discharging
presentations, `FourColor/Present*.lean`, are corun1024/4ct's: they are the reference's
scripts, but the larger hubcap checks are split into finer case analyses than `present*.v`
has, because they were emitted for Lean's kernel. The checks themselves are the same
computations, and lazylean checks them as part of the closure.

## Layout

```
FourColor/RealPlane.lean          the plane, and the statement of the theorem
FourColor/RealPlaneMathlib.lean   the statement's topology is Mathlib's
FourColor/Hypermap.lean, Walkup.lean, Euler.lean, Jordan.lean, Geometry.lean, …
                                  the hypermap theory (see corun1024/4ct for the full map)
FourColor/Color.lean, Chromogram.lean, Ctree.lean, Gtree.lean, CtreeRestrict.lean,
FourColor/GtreeRestrict.lean, KempeTree.lean, Kempe.lean
                                  the reducibility engine: Gonthier's ctree/gtree machinery
FourColor/CfMap.lean, CfContract.lean, CfReducible.lean
                                  configuration programs, contracts, checkReducible and
                                  check_reducible_valid
FourColor/Configurations.lean     the 633 configurations (translated from configurations.v)
FourColor/Reducible/Job*.lean     the reducibility job files (generated, after job*.v)
FourColor/Reducible/Task*.lean, All.lean   the chaining (after task*.v, reducibility.v)
FourColor/Present*.lean           the seven discharging presentations (after present*.v)
FourColor/Complete.lean           the theorem
FourColor/Audit.lean              negative controls, exported and checked with the theorem
scripts/verify.sh                 export and check everything with lazylean
scripts/schedule_reducible.py     the 633 checks under a memory budget
scripts/summarize.py, check.sh, Check.lean, RingSizes.lean, gen_reducible.py, synth_decide.py
verification/SUMMARY.md           the committed result of the verification run
```
